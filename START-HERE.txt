ЛХЛ-76 — комплект для команды развёртывания

СОСТАВ
lhl76-source.tar.gz — исходный код, Dockerfile, зафиксированные зависимости,
схема Prisma, unit-тесты, изображения оформления. Распакуйте в пустой каталог:
tar -xzf lhl76-source.tar.gz -C /path/to/empty/release
Это переносимый снимок исходников, а не история старого рабочего Git.
База, персональные данные, локальные секреты и резервные копии НЕ входят в код.

lhl76-data.tar.aes — отдельный зашифрованный архив полной базы и всех публичных
файлов. Пароль получить у владельца другим каналом; никогда не коммитить его.
Node 22+: node decrypt-handoff.mjs lhl76-data.tar.aes /secure/key.txt restored.tar
Сверить SHA256 зашифрованного файла с CHECKSUMS.json. Скрипт проверяет AES-GCM
до переименования результата. Файл .unverified при ошибке не использовать.
Затем: tar -xf restored.tar -C /path/to/empty/data
Архив содержит database.dump, public-files/ и complete-verification.json.
База содержит существующие аккаунты и хеши паролей: это конфиденциальные данные.

РАЗВЁРТЫВАНИЕ
1. Не запускать seed/reset/db push. Не восстанавливать поверх существующей базы.
2. Создать НОВУЮ пустую PostgreSQL 16 базу и отдельного владельца схемы.
   Восстановить: pg_restore --exit-on-error --no-owner --no-acl
   --dbname=<НОВАЯ_БАЗА> database.dump
   Пароль передавать безопасно через PGPASSFILE/секреты, не командной строкой.
3. Сверить количества и ограничения по complete-verification.json, выборочно
   открыть протоколы. Приложению выдать отдельную роль только с CONNECT,
   USAGE schema, SELECT/INSERT/UPDATE/DELETE таблиц, USAGE/SELECT sequences.
   Никаких SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS и прав CREATE в schema.
4. Создать серверный .env по .env.example с НОВЫМИ AUTH_SECRET и паролем БД.
   PUBLIC_SITE_URL=https://lhl-76.ru. ALLOW_ADMIN_SETUP=0 для перенесённой базы.
   Старые локальные секреты не требуются; смена AUTH_SECRET отзывает старые сессии.
5. Перенести public-files без потери файлов в постоянное хранилище.
   uploads, legacy-media, documents должны быть доступны под /app/public/.
   В compose передать MEDIA_ROOT — абсолютный путь каталога public-files.
   Приложение работает пользователем node (UID 1000); загрузкам нужны права записи,
   оригиналы legacy-media и документы доступны для чтения.
6. Собрать docker compose --env-file /secure/site.env -f docker-compose.production.yml build
   Запустить docker compose --env-file /secure/site.env -f docker-compose.production.yml up -d
   В DATABASE_URL не использовать localhost для внешнего контейнера PostgreSQL.
   БД должна быть доступна по приватной сети/имени сервиса, без публичного порта.
7. Настроить HTTPS reverse proxy к 127.0.0.1:3000. Проверить /api/health,
   /api/ready, фото после прокрутки, документы, вход и сохранение протокола.
   TRUST_PROXY_IP=1 только если proxy перезаписывает X-Real-IP, иначе оставить 0.
8. Настроить и ПРОВЕРИТЬ внешние копии, WAL/PITR и аварийное восстановление.
   Цели и остальные серверные требования — docs/DEPLOY-GATES.txt.
9. Перед финальным переносом согласовать окно без записи и получить свежий
   финальный дамп: пакет отражает время копии, последующие изменения в него не входят.
10. DNS и отключение старого сайта — только после проверки владельцем.

ОБНОВЛЕНИЕ/ОТКАТ
Хранить предыдущий образ с неизменяемым тегом. При откате менять только образ,
оставляя актуальную БД, uploads и limiter. Не восстанавливать старую БД автоматически.
Изменения схемы требуют отдельного плана совместимости и проверки на копии.

ЛОКАЛЬНО БЕЗ DOCKER
Node 22, pnpm; pnpm install --frozen-lockfile; pnpm db:generate; pnpm test;
pnpm build; pnpm start. Подключать только отдельную восстановленную базу.
Все файлы public-files объединить с public до запуска. Секреты не коммитить.

ВАЖНО
Репозиторий приватный. Не менять его на публичный и не загружать в него архив БД.
Подробные результаты проверок передаются отдельным RELEASE-STATUS.txt.
Сигнатуры документов не заменяют антивирус; конфигурация будущего сервера ещё
должна быть проверена. Сборка кода не означает безусловную готовность к публикации.

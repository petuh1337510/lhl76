# ЛХЛ-76 — новая информационная система лиги

Production deployment: [docs/PRODUCTION-DEPLOY.md](docs/PRODUCTION-DEPLOY.md).

Самостоятельная система публичного сайта и административной панели ЛХЛ-76. Текущая локальная база содержит реальные перенесённые данные. Название базы со словом test не делает её тестовой. Перед публикацией сверяйтесь с docs/RELEASE-STATUS.txt и docs/DEPLOY-GATES.txt.

## Технологии

- Next.js (App Router) + TypeScript strict mode;
- PostgreSQL + Prisma ORM;
- CSS design system, mobile-first адаптация;
- Docker Compose для PostgreSQL;
- Vitest для критичной спортивной логики.

## Структура

`src/app` — публичный интерфейс и маршруты.  
`src/lib/domain` — независимая бизнес-логика (например, расчёт таблицы).  
`src/lib/migration` — контракты будущего импорта.  
`prisma` — схема, миграции и тестовый seed.  
`docs` — эксплуатационная и миграционная документация.

Авторизация и административные маршруты уже реализованы; права проверяются на сервере.

## Локальный запуск

1. Создайте файл окружения:

```powershell
Copy-Item .env.example .env
```

2. Установите зависимости:

```powershell
pnpm install
```

3. Запустите PostgreSQL:

```powershell
docker compose up -d
```

4. Для существующей базы не запускайте seed, reset или db push. Для новой среды сначала восстановите проверенную копию в отдельную базу и согласуйте миграции. Сгенерируйте клиент без изменения данных:

```powershell
pnpm db:generate
```

5. Запустите сайт:

```powershell
pnpm dev
```

Откройте `http://localhost:3000`. Вход администратора доступен по `/admin`. Не перезаписывайте существующие .env и .env.local инструкциями первоначального запуска.

## Проверка качества

```powershell
pnpm test
pnpm lint
pnpm build
```

## Управление и безопасность

Все секреты находятся только в `.env`; `.env` нельзя добавлять в Git. Связи `Competition`, `TeamEntry`, `RosterEntry` и `PlayerClassification` сохраняют спортивную историю: у игрока нет поля «единственная команда», а заявки чемпионата и турниров существуют независимо. Удаление ключевых сущностей в будущих интерфейсах будет мягким.

### Автоматические трансляции VK Видео

В серверном файле окружения задайте `VK_VIDEO_CHANNEL_URL=https://vkvideo.ru/@lhl76/lives` и `VK_API_ACCESS_TOKEN` — пользовательский токен VK с доступом к видео. При необходимости можно указать `VK_VIDEO_OWNER_ID` (для сообщества это отрицательное число). Токен нельзя помещать в `NEXT_PUBLIC_*` или вводить на публичной странице.

Страницы «Трансляции» и главная получают видео через официальный VK API; результат обновляется не реже одного раза в пять минут при запросах к сайту. При ошибке VK остаются доступными трансляции, добавленные вручную в админке, и ссылка на канал. Без токена автоматическая загрузка не работает.

### Фотоальбомы ВКонтакте

В админке «Медиагалерея» можно вставить ссылку на альбом сообщества вида `https://vk.ru/album-170455976_313395065`. Сервер получает название, обложку и фотографии через официальные методы VK `photos.getAlbums` и `photos.get`, сохраняет копию ссылок в базе и публикует альбом. На публичных страницах данные обновляются при запросах не чаще одного раза в час; при недоступности VK показывается сохранённая копия. Кнопка «Обновить из VK» запускает немедленную синхронизацию. Требуется серверный `VK_API_ACCESS_TOKEN`; согласно схеме методов VK, для чтения альбомов и фото подходят пользовательский и сервисный ключи, но доступ конкретного ключа следует проверить перед использованием. Без токена существующие альбомы остаются видимыми, но подключение и автоматическое обновление VK-альбомов недоступны. Токен никогда не вводится в браузерную админку и не добавляется в Git.

## Безопасный запуск и условия публикации (28.10.2026)

Рабочая локальная база называется `lhl76_import_test`: слово `test` не делает её тестовой. Никогда не запускать на ней seed, reset, массовый импорт, нагрузочные проверки или восстановление поверх существующих данных. `DATABASE_URL` работающего сайта не менялся. Существующие изменения и оригиналы файлов сохраняются.

### Конфигурация

- `PUBLIC_SITE_URL=https://lhl-76.ru` — подтверждённый владельцем адрес. Это метаданные, не публикация и не изменение DNS.
- Production требует уникальный `AUTH_SECRET` длиной не менее 32 символов. Примеры и запасной секрет отвергаются. Реальные секреты остаются только в окружении.
- Первичная настройка закрывается после появления первого пользователя; в production дополнительно требуется временный `ALLOW_ADMIN_SETUP=1`. После настройки убрать разрешение.
- После изменения пользователя старые сессии отзываются. После обновления старой версии сайта требуется повторный вход; пароли не изменяются.
- За доверенным reverse proxy включить `TRUST_PROXY_IP=1` только если он перезаписывает `X-Real-IP` и прямой доступ к Node закрыт. Иначе используется общий консервативный лимит входа. Общий `RATE_LIMIT_DIR` нужен всем Node-процессам одного сервера; для нескольких серверов требуется согласованное общее хранилище ограничений. Текущая реализация не является распределённым ограничителем для нескольких машин.
- CSP блокирует неподтверждённые скрипты: каждой HTML-странице выдаётся уникальный nonce; в production нет script unsafe-inline/unsafe-eval. HTML не кэшируется публично, кэш данных сохраняется. Inline CSS пока разрешён для совместимости дизайна. Внешние отчёты не отправляются. Реальные трансляции дополнительно проверить на целевом сервере; HTTPS/HSTS настраиваются там.

### Резервные копии и восстановление

Проверенная копия от 28.10.2026 19:13 находится в `backups/final-safety-20261028-191346`, вторая — `D:\LHL76-Backups\final-safety-20261028-191346`. Windows определяет C: и D: как разные диски. Проверено восстановление в отдельный контейнер и базу `lhl76_safety_restored` на `127.0.0.1:55432`: все 37 таблиц, агрегированные отпечатки всех строк и ограничения совпали. Восстановление самого дампа заняло 3,55 с; это НЕ полный срок аварийного восстановления. Все 62 исходных локальных файла прошли сверку после распаковки. Подтверждение — `verification.json`. Копии не перезаписывать.

`scripts/backup-local.ps1` создаёт уникальные копии БД и всей папки public на двух дисках и сравнивает SHA-256. Он не восстанавливает, не удаляет и не ротирует данные. Перед запуском проверить выбранные контейнер, пользователя и имя базы. Файловые удаления/перезаписи не должны идти одновременно с архивированием. Новые неизменяемые файлы загружаются под уникальными именами.

Порядок восстановления: создать отдельную пустую PostgreSQL 16 с другим именем и портом; проверить адреса источника и назначения; восстановить custom-дамп через `pg_restore --no-owner --no-acl --exit-on-error`; распаковать файлы в отдельный каталог; сравнить все таблицы, связи, контрольные суммы и выборочные протоколы. Никогда не восстанавливать поверх рабочей базы автоматически. В инциденте сохранить новую копию повреждённого состояния и новые записи, затем согласовать план восстановления с владельцем.

Предложенная, **не включённая** политика: ежедневный backup, копия перед согласованными опасными изменениями, 14 дневных + 8 недельных + 12 месячных поколений, ежемесячное пробное восстановление. Для матчей, которые нельзя потерять между копиями, нужны WAL/PITR и согласованные RPO/RTO. Сейчас автоматического расписания/PITR нет: возможна потеря изменений после последней копии. D: защищает от отказа C:, но не от утраты компьютера или шифровальщика. Шифрование, отдельный ключ восстановления и отключаемая/внешняя копия требуют настройки владельцем; ничего во внешние сервисы не отправлялось. Существующие копии не удаляются автоматически.

### Модель угроз и границы защиты

- Вход: перебор, раскрытие наличия пользователя, кража сессии. Реализованы одинаковые ошибки, лимиты, scrypt, HttpOnly/Secure/SameSite, проверка актуальной роли и версии пользователя на сервере.
- Административные API: обход middleware, подмена роли/ID, CSRF и слишком большие тела. Обработчики отдельно проверяют доступ; мутации сверяют Origin/Host; тела ограничены по объёму и времени. Секретарю доступны только предусмотренные маршруты матчей. Протокол проверяет принадлежность игроков командам. Ролевой доступ не заменяет отдельного назначения секретаря на матч: такой модели в текущей схеме нет.
- Данные: протокол сохраняется транзакционно, версия `updatedAt` защищает от устаревшей формы, блокировка дивизиона сериализует пересчёт. Формулы статистики не изменены. Это не означает, что конфликтное редактирование уже проверено во всех формах админки.
- Файлы: проверяется декодирование растров, лимит 40 Мп, размер, сигнатуры документов и видео, серверные UUID; SVG/HTML не принимаются. Одновременно обрабатываются не более двух upload-запросов на процесс. Проверка сигнатуры не заменяет антивирус документов; антивирусный сервис не подключён.
- Внешние ресурсы: локальная карта проверенных старых файлов, ограниченные адреса видео-превью, запрет редиректов, тайм-ауты и предел ответа превью. Внешние картинки проходят отдельную проверку CDN, DNS и публичного IPv4 с закреплением проверенного адреса в HTTPS-соединении; редиректы запрещены. Прямые внешние URL для оптимизатора Next отключены. Ограничены очередь, число одновременных загрузок и размер кэша Next (1 ГиБ). Дополнительные правила egress на сервере всё равно нужны; инфраструктура не менялась.
- Журналируются успешные административные операции и входы без паролей/токенов. `/api/health` и `/api/ready` не раскрывают настройки. Нужно настроить мониторинг 5xx, p95, памяти, диска, пула БД, давности и ошибок резервных копий. Внешней телеметрии нет.

### Что обязательно проверить на реальном сервере

HTTPS, закрытые служебные порты и непубличную БД, отдельные минимальные права приложения и миграций, постоянные каталоги загрузок/лимитов/резервных копий, ограничения размера/времени запросов и числа подключений, дисковую квоту image-кэша, защиту DDoS на хостинге/CDN/WAF. Локальный PostgreSQL сейчас публикует порт Docker: это нельзя переносить в production без закрытия доступа. Firewall и инфраструктура в этой задаче не изменялись.

Двухфакторная аутентификация: отдельный согласованный этап — TOTP или WebAuthn, подтверждение подключения, одноразовые коды восстановления, резервный администратор и проверка восстановления доступа. Принудительно не включена.

Не считать локальные тесты доказательством полной защищённости. На 29.10.2026 установлены deepmerge-ts 8.0.0, Vitest 4.1.12 и Vite 7.3.7; проверка pnpm audit не обнаружила известных уязвимостей. Prisma осталась 6.19.3. Проверку зависимостей повторять перед публикацией.

### Исправления независимого аудита от 29.10.2026

- СЕКРЕТАРЬ намеренно имеет доступ ко всем матчам, но не к пользователям и остальным редакторским разделам. Это согласованное правило, не ошибка назначения матчей.
- Приложению нужна отдельная роль PostgreSQL без SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS, владения таблицами и CREATE в public. Права миграций хранятся отдельно и не передаются приложению. Локальное подключение переключено после восстановления свежего backup на копии.
- Входной скрипт контейнера больше не запускает db push. Изменения схемы выполняются отдельно после backup и проверки на копии; обычный рестарт не меняет схему.
- `docker-compose.production.yml` — шаблон одного экземпляра за HTTPS reverse proxy. Секреты вводятся через серверное окружение, DATABASE_URL — ограниченная роль, сама БД должна быть в закрытой сети. Не использовать демонстрационные реквизиты из dev-compose.
- Каталог `/app/state/limits` находится на постоянном томе. Его нельзя удалять при рестарте. Для нескольких серверов нужен отдельный общий лимитер; этот шаблон не разрешает multi-host deployment. При отсутствии RATE_LIMIT_DIR production-вход не обходится без лимитов.
- Docker собирает standalone на Linux и не переносит весь build node_modules в runtime. Для локальной Windows-сборки standalone не обязателен; `NEXT_STANDALONE=1` включает упаковку.
- Ссылки редакторских материалов проверяются при записи на сервере и перед отображением. Разрешены HTTPS и допустимые локальные пути; javascript/data/file, сетевые пути, credentials и буквальные IP не принимаются. Существующие записи базы массово не переписываются.
- Проверка: `pnpm test`, `pnpm audit`, production build; `node --env-file=.env.local scripts/check-security-fixes.mjs` использует только конкретную проверенную восстановленную копию. Скрипт привязан к backup этой проверки: перед повтором с новой копией проверить его параметры, никогда не подставлять рабочую базу.

Свежая копия: `backups/approved-2026-10-29T12-48-10-733Z`, вторая — `D:\LHL76-Backups\approved-2026-10-29T12-48-10-733Z`. Восстановление 37 таблиц и проверка 1456 файлов выполнены; время восстановления дампа 4,54 с, не полное время аварийного восстановления. Отчёт — `complete-verification.json`. Прежнее окружение сохранено локально в закрытом от Git каталоге backup; не публиковать его и не прикладывать к отчётам.

Изолированные HTTP-проверки: `node --env-file=.env.local scripts/check-isolated-readiness.mjs`. Скрипт проверяет отдельные контейнер, порт и имя базы, создаёт временные учётные записи только в восстановленной копии, проверяет запреты и конкурентное сохранение, затем удаляет только созданные им тестовые учётные записи. Старый `verify:match` намеренно останавливается до работы с данными: прямые вызовы обработчиков без авторизованного HTTP-контекста более не поддерживаются.
